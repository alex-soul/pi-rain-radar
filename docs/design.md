# Current design

## Implemented slice

An ordered loop of up to 13 complete observed radar composites spanning the latest two hours over a locally prepared regional basemap. Defaults are Coventry (52.40801, -1.51041), with a 1280 × 720 canvas at Web Mercator zoom 8 and overview zoom 5. The Map tab changes the centre, displayed name, both zoom levels and display time zone. This is a regional orientation map, not a street map.

The map fills the entire display behind a compact theme-matched translucent footer (76 pixels at the target size). A compact top-left stack contains clock, theme, Overview, MinuteCast and History controls, with radar health in the footer handle and current weather in the top dock; there is no heading or banner. At other aspect ratios, the map fills the viewport by cropping symmetrically rather than adding empty bands or stretching geography.

Node.js 24 LTS serves a dependency-light HTML/CSS/JavaScript frontend. Sharp validates, scales, crops, and composes radar tiles into two transparent PNGs per timestamp. The browser overlays those PNGs on the bundled SVG basemap. All display assets are local; there are no CDN fonts, map tile requests, or provider calls from the browser.

The backend checks RainViewer every five minutes, sorts/deduplicates `radar.past` into a bounded two-hour history, and retrieves only missing frames using viewport-dependent tiles, capped at source zoom 7, sequentially (12 tiles per timestamp at the supplied defaults). Requests are spaced by at least 850 ms (about 71/minute), including metadata. Zoom-7 radar is enlarged twofold for the zoom-8 display; this does not add source detail. Tile origins and the basemap use the same projection. Metadata host/path validation limits tile fetching to the expected RainViewer service.

A frame is published only after all requested tile images decode at the expected dimensions and composition completes. This verifies transport/composition, not that the provider has supplied every rain observation. The PNG and then manifest are renamed into place. Last-good state is persisted in a named Docker volume and loaded on restart; a failed fetch keeps that state. A hash of the viewport configuration is recorded in the manifest and image filename, preventing reuse of radar for a different centre, zoom, or canvas size and preventing browser cache collisions. The history manifest is replaced atomically with the available complete main/overview pairs. A failed timestamp is skipped so it cannot block later complete observations. Missing pairs still listed within the live window are retried on the existing five-minute schedule, including when no newer timestamp appears; completed views are reused. The window is bounded relative to the newest successfully completed observation, retaining last-good history if all newer frames fail. A historical gap uses the existing missing-slot indication; acquisition health remains in error when the newest eligible observation cannot be completed. Cleanup retains seven days of timestamped images plus a one-hour buffer. The current and previous sets plus the newest 26 images remain protected for handover/partial progress even during extended outages. Cleanup also runs after failed acquisition. Startup restores valid cached frames, requiring both views to decode successfully. Older main-only caches are upgraded by acquiring the missing overview images; they are not offered to the paired player until ready.

The frontend checks local status every 15 seconds and fully decodes both images for every timestamp in each incoming sequence before switching at a loop boundary. Images remain preloaded for playback without network calls. Frames advance every 650 ms, with a 1600 ms hold on the latest frame. Pause/resume and a keyboard-accessible timeline allow inspection; scrubbing pauses. While paused, incoming history waits until playback resumes. The 48 px, left-aligned and vertically centred footer clock follows the displayed observation, with its 20 px date alongside, using abbreviated weekdays and three-letter months such as Sun, 13 Sep (configured time zone). The date uses an 8 px clock gap to fit the existing observation area without moving the playback row at the target display size. The footer handle carries green/amber radar health and its expanded footer shows latest-data age (minutes below 60; decimal hours to one place from 60 minutes), using the newest frame known to the app even when playback is paused on an older sequence. Playback state and Past/Latest labels are omitted. The handle has an accessible label and tooltip. A failed refresh, lost local connection, or latest-frame age of 30 minutes turns the handle amber. Empty-cache acquisition shows progress. These are the current fixed playback timings.

## Data semantics and sources

RainViewer is the selected provider for ongoing personal appliance use, beyond the prototype. Its best-effort service has no SLA; local caching and visible freshness remain essential. A paid replacement is not planned unless observed limitations justify it.

- [RainViewer Weather Maps API](https://www.rainviewer.com/api/weather-maps-api.html): metadata timestamps identify composite frame generation, not the exact observation time of every underlying radar. The display labels them as frame times. Only past radar is used.
- [RainViewer transition constraints](https://www.rainviewer.com/api/transition-faq.html): plan around maximum zoom 7, Universal Blue, and 100 requests/IP/minute. Both views share the same request limiter. A completely cold 13-frame sequence requires 156 tile requests plus metadata, spread over roughly 2–3 minutes; each new timestamp needs 12 tiles.
- [RainViewer terms](https://www.rainviewer.com/api.html): personal-use API with best-effort availability and recommended local caching. The footer provides visible linked provider credits. See THIRD_PARTY_NOTICES.md for the separation between software licensing and provider data terms.
- [Natural Earth](https://www.naturalearthdata.com/about/terms-of-use/): public-domain geographic data permits bundling and offline use. A compressed geometry/name dataset in `assets/` is pinned to upstream revision `ca96624a56bd078437bca8184e78163e5039ad19`. It is loaded by a temporary backend worker during map preparation. Default generated assets remain versioned product assets.

## Current gaps

- Hardware deployment and on-device map preparation performance remain to be validated.
- RainViewer coverage/no-data masks are not yet shown. An uncoloured region must not be interpreted as a verified absence of rain.
- The current view uses zoom 8. Animation pace and usability still need evaluation; Natural Earth remains generalized cartography.
- Sequence publication, partial-failure recovery, and offline cache restoration have tests. Extended offline operation, power interruption, and Pi/ARM64 performance remain to be validated.
- Docker runtime is pinned to a Node 24 Bookworm multi-platform image digest supporting amd64 and arm64. Update the digest deliberately and rerun validation.
- The initial public release is MIT-licensed and marked as a pre-release. No published container image is supplied; Compose builds from source. On-device validation remains pending.

## Future enhancements

- [Playback window and timing settings](#deferred-playback-window-and-timing-settings) are deferred until Pi baseline tests: retain two hours by default, optionally three/four hours, with adjustable frame speed and final hold.

- Historical current-weather/forecast snapshots are deferred. Both weather widgets remain current during radar history; any future archive must distinguish issued forecasts from observations and retain location and timestamps. No weather archive or -1h chart is implemented.

- **Configurable render resolution — nice to have, deferred; no implementation planned.** Consider tested size presets in Map settings, retaining 1280 × 720 as the default. Render size should remain independent of screen resolution. Any implementation must derive marker/label positions, scale, SVG viewport and overview extent from the chosen dimensions, and preserve geometry-specific cache/history isolation. Keep rendering on the backend and the browser image-based. Bound larger sizes and measure preparation time, playback memory, tile requests and archive storage on the target Pi before enabling them; more pixels do not increase the provider's source detail.

## Radar acquisition timing and recovery

New observations have a five-minute settling window measured from the start of the poll that first discovers them in the provider manifest. The scheduler and first-seen record share that timestamp, so manifest request latency does not accidentally add another five-minute cycle. The existing five-minute poll continues; no tiles are fetched for a waiting timestamp. First-seen times are bounded to the current manifest and persisted atomically in settling.json so normal restarts retain the wait. Missing/invalid state restarts the wait safely. On empty-cache startup only older observations may load immediately; the newest still waits. A lone newest observation leaves the initial loading state until eligible.

While waiting, retain the last complete sequence. When eligible frames are ready, merge still-relevant cached history, bounded to 13 frames/two hours ending at the latest successfully completed observation, and publish the main/overview pair atomically. Startup may temporarily supply 12 frames covering 110 minutes; the slider still spans two hours, with the absent slot marked. Poll timing can make the wait longer than exactly five minutes. Freshness continues to use the displayed cache's newest observation time. This reduces exposure to early provider revisions without adding tile requests, but cannot guarantee source completeness or detect later revisions to cached images. Existing cached observations are not repaired/refetched.

The expanded footer shows Next in N min only while a new observation is pending; it estimates the eligible scheduled backend check. Fetching… indicates active sequence acquisition. Existing local status polling carries this state without additional provider requests. Network/refresh failures suppress the estimate; freshness colour rules remain unchanged.

Latest and Next share a small muted font, separated by a middle dot, with no italics or approximation symbol.

Age uses compact wording such as Latest 16 min or Latest 1.5 hours, without an ago suffix.

On recovery when the provider's newest observation is at least 30 minutes ahead of the cached newest, older listed history bypasses settling, including any previously pending wait. Only the newest observation retains its first-seen delay. This also applies on restart with stale persisted history. Catch-up starts on the next successful scheduled manifest check; acquisition still takes time and last-good playback remains until the available complete pairs are published. Browser/OS wake does not currently guarantee an immediate backend check.

## Settings security

A bottom-right cog sits 8 px above the footer. Screen interaction reveals it independently of both docks; it disappears after 15 seconds idle, except while a dialog or held pointer is active. It opens settings directly on new installations. PIN protection is optional and off by default, with no setup prompts or reduced functionality. The PIN tab enables protection with a new six-digit value and confirmation, changes an enabled PIN after unlocking, or disables it. The PIN tab uses two aligned six-box rows with masked single-digit inputs, numeric keyboards, automatic advance to the next row/Save, paste filtering and Backspace/arrow correction. When enabled, access still uses the six-digit touch keypad. Existing salted PIN records remain enabled on upgrade.

- The PIN tab writes a random-salt scrypt hash to `/data/settings/pin.json` (file mode 0600, directory 0700). The persistent Docker volume is outside the repository/image. No plain PIN is retained. Disabling writes an atomic `{ "disabled": true }` record and removes the stored hash. Missing records mean protection is off; unreadable records fail closed. `node src/setup-pin.js` remains the compatible interactive host recovery path. No argument, --set, --reset and --enable all choose and enable a new PIN with hidden input; --disable atomically removes protection, and --status reports enabled/disabled without exposing the hash. Recovery requires host/Docker access, not the old PIN, and preserves other data. See the Quick Start recovery guide. Host administrators with volume access remain trusted.
- The backend checks the PIN and grants a random bearer token held only in browser module memory. Tokens expire after five minutes, are revoked on dialog close/page hide, and do not survive server restart. PIN changes invalidate existing sessions; browser enable/change closes settings, while disable keeps them open without a session. Unprotected settings have no five-minute expiry. An abruptly disconnected client leaves at most the remaining five-minute session lifetime.
- Failed attempts have a shared increasing delay (2 seconds up to 5 minutes), persisted across restarts. Only one PIN verification or configuration change runs at a time; competing first-time enrollments cannot overwrite the winning PIN. A successful unlock resets the delay; resetting the PIN does not bypass an active delay.
- `/api/settings` and its write routes allow access without a bearer token while PIN protection is off. When enabled, the backend requires a valid session even if someone manually reveals the HTML. Future settings read/write routes must use the same authorization check; POST `/api/settings/openweather` uses the same optional-PIN authorization and same-origin JSON checks, with bounded input. It stores/replaces or removes the key; GET settings returns PIN-enabled state, whether a key is configured, and current non-secret map configuration. POST `/api/settings/pin` uses the same origin checks, a 256-byte body limit and current authorization before enabling, changing or disabling protection. Stored PIN hashes and API keys are never returned. Without PIN protection, anyone who can reach the app can edit configuration or replace/remove the provider key.
- Mutations require JSON and reject cross-origin requests. Tokens/PINs are never placed in URLs or localStorage. Responses are no-store. There are no new dependencies or background polls; cryptographic work happens only at setup/unlock. UI expiry uses a one-shot timer while settings are open.
- Default Compose remains bound to loopback. Plain HTTP is suitable for the local kiosk connection; use an SSH tunnel or trusted HTTPS reverse proxy for remote administration. The PIN does not encrypt network traffic or make this an Internet-facing service. Pi runtime performance remains to be measured.

## Stored radar history

The History control opens a touch-friendly date/time picker listing only stored, complete main/overview pairs for the current map configuration. Choose the right end of a two-hour window; the timeline labels that end and two hours earlier. Playback uses the available frames, at most 13. Missing intervals are not synthesized: the fixed-slot slider marks gaps with muted amber and the total frame count indicates a short sequence; the player steps through the observations actually available. This does not detect missing weather within an otherwise valid provider image. Both maps share the selected sequence. In history mode the slider position follows the actual timestamp within that two-hour axis; it jumps across gaps, and scrubbing selects the nearest available observation. Arrow keys step through available frames.

Images are retained for seven days plus a one-hour cleanup buffer. A selectable window must start within the seven-day period; therefore its end is at least two hours after the retention boundary. History accumulates only while this installation acquires observations; there is no historical backfill. Changing the map configuration prevents reuse of mismatched images.

An in-memory timestamp index is reconstructed once from paired PNG filenames at startup and updated as pairs finish. There is no database, additional tile download, re-rendering or background archive scan. Existing acquisition cleanup scans the retained filenames every five minutes. GET `/api/archive` returns available end timestamps; GET `/api/archive?end=<unix-seconds>` returns one window, or 404 if unavailable. Both responses disable HTTP caching.

Choosing history replaces the browser's active sequence after both views decode. During the transition the previous and incoming window coexist temporarily, as with ordinary live handover. After adoption, the app retains only the selected decoded sequence; status polling continues for acquisition health without preloading live images. Browser-managed HTTP caching remains independent. Acquisition and live publication continue normally.

The compact picker places Date and Time side by side with a full-width Show action below, without explanatory text. Loading/errors remain visible when needed. After loading, the History toolbar control expands with the selected two-hour range and stays expanded until returning live. It uses numeric dates without weekday or ordinal suffix and three-letter months, for example `12 Aug 09:50 - 11:50`; windows across midnight repeat both dates, for example `11 Aug 22:30 - 12 Aug 00:30`. Clicking the date range reopens the picker without collapsing it; clicking the History icon returns to live. Hiding the History dock removes both manual targets but does not stop automatic return. A fixed ten-minute deadline starts after a historical window loads; choosing another window restarts it, while pause/scrub do not. Timeout, page visibility and pageshow checks return to Now; refreshing also starts live. A failed live reload keeps the last images with the expanded History control retained until retry succeeds; the icon tooltip/accessibility label indicates the pending return. No per-viewer file leases are needed for casual viewing: the one-hour buffer exceeds the viewing deadline, and wake checks leave expired history. If a file becomes unavailable, selection fails without replacing the current map.

Storage depends on actual weather/compression. Measure image pairs on the target device; estimate seven days as average pair bytes × 144 × 7, plus buffer and filesystem overhead. Pi memory/SD performance and long-term operation still need hardware validation.

The expanded History dock has one two-pixel teal countdown outline around the entire pill, with no circular icon border. An SVG progress stroke replaces that edge clockwise from twelve o'clock over the ten-minute viewing period: the muted inactive control outline for the current theme. It is updated once per second by the existing clock tick, using the actual return deadline and clamping elapsed progress. A new selection restarts the ring; tapping the History icon returns immediately, while tapping its date range reopens the picker. No additional timer, continuous animation, provider request or backend processing is introduced.


## OpenWeather acquisition

OpenWeather health is shown by the weather drawer handle; radar health is shown by the persistent footer handle. Overview and MinuteCast have no separate LEDs. API settings shows the live connection result and last successful-fetch timestamp, with transient saving or actionable validation errors when needed. HTTP failures include the actual status code and a safe explanation; provider bodies and credentials remain private. Health uses existing status polling and the minute-level rendering guard, adding no network requests or timers.

`src/weather.js` shares one One Call 3.0 response for current temperature/feels-like/wind, optional gusts and next-hour precipitation. It uses the radar centre coordinates, metric provider units and local wind conversion to mph; hourly/daily/alerts are excluded. Requests are HTTPS with redirect rejection, 15-second timeout, bounded response bytes and validation of numeric fields/timestamps. Provider response text and request URLs are never logged or returned in errors.

The existing five-minute backend scheduler invokes a guarded refresh: at least ten minutes between attempts, no overlap, no requests while unconfigured. Explicitly saving a key requests an immediate check, including re-saving a key after activation. A persistent thirty-second setup cooldown bounds those manual checks; disabling/re-enabling or restarting does not bypass it. Saves during the cooldown return HTTP 429 with Retry-After and leave the stored key unchanged. Normal background polling retains its ten-minute interval. An off-cycle attempt may wait up to fifteen minutes for the following scheduled attempt. Last-good normalized data and the next-attempt timestamp persist atomically in `weather.json`, scoped by centre coordinates. Normal restarts respect the schedule. Failed requests retain last-good data; retry errors are sanitized. Saving the key uses the settings authorization policy (PIN session only when protection is enabled); `settings/openweather.json` uses mode 0600 within the protected settings folder, outside image/source. This is restricted-file storage, not encryption against host administrators.

Weather metadata joins `/api/status`, so browsers add no polling endpoint/timer. The renderer short-circuits when cache identity, minute and availability/error are unchanged; radar frame playback does not redraw the chart. Temperature, feels-like and wind retain one failed poll, tinting only their numeric spans in the same theme-specific muted amber as retained gusts. Two consecutive failed polls or thirty minutes since the provider observation produces dashes. The failure counter saturates at two and persists with the sanitized error in weather.json so restarting cannot restore fresh styling; successful responses reset it, and location changes/key removal clear it. HTTP errors, network failures and rejected responses count once per attempted request, never per browser/status poll. Icons and units are not dimmed. Gust retention remains independent. Past forecast minutes are discarded from the visible chart as wall time advances; a fully expired/missing forecast shows unavailable. No data is converted into fabricated dry intervals. Provider attribution appears when configured. Current widgets stay current during radar history; no weather snapshots/archive or past forecast reconstruction are implemented.

Automated validation uses mocked provider responses and an isolated test UI. Each installation must confirm its own key entitlement, local forecast availability/quality and combined account usage. Pi resource measurements remain unverified.

The successful OpenWeather connection message includes the last successful fetch timestamp in the configured zone (for example, 14 Sep 13:17).

Dashboard controls share theme-specific muted one-pixel inactive outlines and teal two-pixel selected/expanded outlines, including the clock. The History countdown replaces its teal segment with a one-pixel inactive-colour segment, without leaving teal underneath. The weather drawer is 540 px wide with matching rounded trapezoid geometry, providing clearance for double-digit readings and wind units; the collapsed handle remains unchanged.

At the medium footer breakpoint (520 px and above within the compact/portrait layout), OpenWeather attribution occupies its own right-aligned line beneath Radar/Map attribution, with the rain legend above both. Wide layouts and the smallest stacked layouts keep inline attribution; the separator is hidden only when the weather credit moves to its own line.

The frame counter colours only its total: teal for a full 13-frame window and amber below 13. The total is semibold and fully opaque, with subdued teal/gold in dark mode and deeper green/amber in light mode for contrast against the translucent footer. The current position reserves two right-aligned digit columns, preventing the slash/total from shifting at frame 10. The slash uses a more subdued grey. This indicates available frame count, not completeness of rain tiles inside each image, and applies to live and historical playback.

The weather drawer grip displays OpenWeather health while expanded or collapsed: teal for usable data, amber for errors/missing/expired data or awaiting the first configured response, and white when unconfigured. It reuses the MinuteCast health calculation and existing refresh cycle; the drawer outline is unchanged.

## Runtime map configuration

Map settings offers a Preview action showing Main map and Overview images with projected labels, centre markers and local-view outline. Back returns to the proposed fields; Apply commits them through the normal flow. Preview prepares only offline basemaps in one bounded temporary slot; it neither changes the active view nor acquires radar/weather. It shares the existing single map-job guard and reuses the prepared assets on Apply.

The Map tab sends a bounded configuration authorized by the optional-PIN policy to POST /api/settings/map. A single backend job prepares versioned offline assets in a short-lived worker and a matching radar sequence before committing settings/map.json. Existing clients keep their view during preparation, then reload when the map identity changes in the existing status poll. Archive requests carry that identity and reject mismatched views. Image hashes remain geometry-specific, allowing cache reuse without mixing locations; metadata manifests are also keyed for non-default geometries. See the development guide for field bounds, data layout and recovery behaviour.

Map Apply introduces temporary work rather than ongoing rendering: an isolated Windows laptop test preparing Paris completed in about 0.9 seconds with roughly 384 MiB peak process RSS. This is a preparation measurement, not a steady-state or Raspberry Pi measurement. The geometry worker exits afterward; new radar downloads can take several minutes and retain provider pacing. Validate peak memory and timing on the Pi before treating its performance as proven.

## Deferred: playback window and timing settings

Optional future enhancement, after baseline playback and memory use have been measured on the target Raspberry Pi. Keep the current two-hour window and playback timings as defaults. Consider settings for a longer window (for example three or four hours), time per frame/playback speed, and the hold on the final frame before looping. This is a playback-window choice, separate from seven-day archive retention and the ten-minute History auto-return.

Reuse already acquired frames from the matching map archive; availability remains best effort, with no provider backfill or extra polling implied. A four-hour window at ten-minute spacing has 25 expected slots instead of 13; slider positions, gap markers, counters and History window labels must follow the selected duration. Decide whether the setting applies to both live and History playback when designing the feature. Preserve paired main/Overview timestamps.

Longer windows can increase browser image decoding, memory and transfer from local storage even though acquisition is unchanged. Measure 2/3/4-hour windows and timing choices on the Pi 4 / 2 GB before implementation is accepted; use bounded frame loading if needed, without introducing continuous interpolation or GPU effects. No implementation is scheduled yet.
